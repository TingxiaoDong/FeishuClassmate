## A1 网关对所有会话的消息都会回复【严重】

**位置**：`src/runtime/bot-gateway.ts:478` `handleMessage`。只排除了 `sender_id` 为 `bot` / `system` 的消息，没有判断：
- 机器人是不是这个会话的成员；
- 是不是单聊，或者群里有没有 @ 机器人。

**现象（已实测）**：u1 给 u2 私聊发「晚上一起吃饭？」，网关调了大模型，机器人往这个私聊里回了一条消息。

**影响**：同学之间的私聊被发给大模型（隐私问题）；机器人在群里对每条消息都插话；每条消息都要花一次大模型调用。

**修改建议**
1. 在 `handleMessage` 开头加过滤，只处理两类消息：
   - 机器人参与的单聊（`chat_type === 'p2p'` 且成员包含机器人）；
   - 群聊里 @ 了机器人的消息（看消息的 mentions 字段；需要的话请后端在 bot 事件里带上 `chat_type` 和 `mentions`）。
2. 群里 @ 机器人时，把 @ 部分从 `text` 里去掉，再交给模型。
3. 「确认 / 取消 / 停」这类控制词（`tryTextAnswer`、`STOP_COMMANDS`）也要先经过这道过滤，避免别的会话里的文字被当成回答（服务端也会校验，这里是双保险）。
4. 后端也会在 WS 层只推送机器人所在会话的消息（B1），两边都做。

**验收**：补网关单测：非成员会话的消息、群里没 @ 的消息都不触发 `runSession`；单聊和群里 @ 会触发。

## A2 确认卡片没有写明要放行的具体操作【严重】

**位置**：`src/runtime/agent-runtime.ts:235-243`，确认通过后只把 `cardId` 交给工具（`ctx.confirmation = { cardId }`）；网关发卡片时（`confirmerFor`）也没有记录这张卡对应哪个接口、哪个对象。

**影响**：服务端只能验证「同学 10 分钟内点过确认」，验证不了「确认的就是这次删除」，同一张卡可以被重复使用、拿去删别的东西（详见后端 B3）。模型被文档或消息里的恶意内容诱导时，护栏挡不住。

**修改建议**（和后端约定字段后一起上线）
1. 确认请求（`input.confirm`）里带上这次调用要发的 `method`、路由模板、`target_id`（从工具参数里取，删除类工具一般就是路径参数）。
2. 网关发卡片时把这些写进卡片内容的 `bound_action`。
3. 工具执行时一张卡只用一次：同一会话里的下一次高风险调用要重新发卡确认，不要复用上一张卡的 id。
4. 卡片上的说明文字（`preview` / `summary`）要写出具体对象（如「删除表格『实验记录』」），让同学知道自己确认的是什么。

**验收**：配合后端测试：确认删除 A 后，再让模型删除 B，会重新弹卡片；手动复用旧卡片 id 被服务端拒绝。

## A3 工具没配风险策略时默认按「只读」【较大】

**位置**：`src/runtime/agent-runtime.ts:224-232`

```ts
let risk: ToolRisk = 'read';
...
risk = policy?.risk?.(params) ?? 'read';
...
} catch { /* 策略函数出错按只读处理，不影响调用 */ }
```

**影响**：删除类操作还有服务端黑名单兜底；但「移动 Temi」这类物理动作、各种修改类工具，只要注册时漏配一次策略，或者策略函数抛异常，就会不经确认直接执行。今天后端新增了接口（工具目录要重新生成，见后端 B4-1），新工具更容易漏配。

**修改建议**
1. 没配策略时默认 `risk = 'write'`；根据 HTTP 方法推断更好：GET → read，DELETE → destructive，其他 → write。
2. 策略函数抛异常时按 `destructive` 处理（需要确认），并通过 `onError` 上报，不要悄悄降级。
3. 物理动作类工具（Temi 等）在 `registerTool` 时强制要求 `policy`，没有就直接抛错。
4. 加一个启动时的自检测试：遍历所有已注册工具，非 GET 类工具都必须有显式策略。

**验收**：单测：没配策略的 POST 工具被识别为 write；策略函数抛错时会走确认；物理工具不带策略注册会报错。
