# ClassmateOS 后端对接说明

对应《前端接口需求文档》。本次把后端按文档重写：P0、P1 全部完成，P2 完成了大部分（见文末「还没做的」）。

## 1. 怎么启动

```bash
# 内存模式（开发联调，重启后数据丢失）
pnpm classmateos

# PostgreSQL 模式（数据持久化，启动时自动建表，可重复执行）
DATABASE_URL=postgresql://user:pass@localhost:5432/classmateos pnpm classmateos
```

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `DATABASE_URL` | 不设 = 内存 | 设置后用 PostgreSQL；自动执行 `schema.sql`（23 张业务表）和 `schema-platform.sql`（账号 / IM / 文件 / 日历 / 任务 / 文档 / 设备 / 自定义数据表定义） |
| `CLASSMATE_OS_PORT` | 8080 | |
| `CLASSMATE_OS_SECRET` | dev-only-secret-change-me | 令牌签名密钥，**生产必须改** |
| `CLASSMATE_OS_BOT_TOKEN` | dev-bot-token | 机器人网关令牌 |
| `CLASSMATE_OS_USERS` | admin/admin、demo/demo | 种子账号 JSON：`[{user_id,name,password,role,department?,title?,email?}]`。**只在库里没有这个账号时插入**，已有账号不会被覆盖（改密码用管理员接口） |
| `CLASSMATE_OS_FILE_DIR` | PG 模式 `./data/files`，内存模式系统临时目录 | 上传文件存放目录 |
| `CLASSMATE_OS_MAX_FILE_MB` | 200 | 单文件上限，超出返回 413 |
| `CLASSMATE_OS_QUOTA_GB` | 10 | `/files/usage` 返回的配额 |

## 3. 前端需要知道的行为

**通用**
- 错误一律 `{ "message": "中文说明", "code"?: "..." }`；参数错误 422 + `code: "VALIDATION_FAILED"` + `errors: [{field, message}]`
- 常用 code：`UNAUTHORIZED`、`ACCOUNT_DISABLED`、`REFRESH_EXPIRED`、`CHAT_NOT_FOUND`、`CHAT_NOT_MEMBER`、`CARD_ANSWERED`、`CARD_EXPIRED`、`FILE_TOO_LARGE`、`DOC_CONFLICT`、`CURSOR_NOT_FOUND`、`NOT_FOUND`
- 带 `content-type: application/json` 但没有请求体的请求（如 DELETE）不会再报 400
- 列表接口统一带 `total`；分页用 `page_token`（没有更多时不返回或为 null）
- 新增 `GET /api/v1/health`

**认证**
- access_token 2 小时，refresh_token 30 天；refresh 每用一次就轮换，旧的立即作废；`POST /auth/logout` 吊销
- refresh_token 当 Bearer 用一律 401
- 登录失败的 message 保持 `invalid credentials`
- 管理员接口：`POST /users`（加人）、`PATCH /users/:id`（改资料、禁用、重置密码）；普通成员 `PATCH /users/me` 只能改头像、签名、电话

**消息**
- 会话列表按最后活动时间倒序（置顶靠前请前端按 `pinned` 处理），带 `unread_count`、`last_message`、`last_read_message_id`、`pinned`、`muted`、`kind`
- `POST /chats {chat_type:"p2p"}` 对同一个人去重：已存在返回 200 + 原会话，新建返回 201
- `name="我的云盘"` 且没有其他成员的会话自动标成 `kind:"drive"`，发进去的自己的文件自动登记到云盘（过渡期约定保持可用）
- 群聊改名 / 改公告 / 加人 / 退群 / 移人都会插入 `msg_type:"system"` 消息
- 群主退群自动转给最早加入的成员
- 消息分页：默认和 `before_message_id` 倒序；`after_message_id` 正序；`page_size` 最大 500
- 发送者自己发的消息自动算已读
- `client_msg_id` 重复时返回 200 和原消息（不重复入库）
- 撤回：发送者 2 分钟内（管理员不限），撤回后 `recalled:true`、`content:{}`
- 卡片：回答后 `content.answer = {user_id, action, answered_at}`；机器人可调 `POST /bot/cards/:card_id/expire` 标记 `content.expired = true`

**实时事件**
- 用户 WS 只推当前用户有权看到的事件；`card.action` 只给 bot WS
- `since` 断点续传：找不到时先发 `{"event_type":"resync.required"}`
- 心跳：每 30 秒 WS ping 帧 + 文本帧 `{"event_type":"ping"}`；客户端发 `{"type":"ping"}` 回 `{"event_type":"pong"}`
- 关闭码：4401 令牌无效 / 过期（连接中令牌过期也会 4401），4403 账号被禁用
- 事件缓冲在进程内存（最近 2000 条），服务重启后旧 `since` 会收到 `resync.required`

**文件**
- 下载响应带真实 `Content-Type`、`Content-Disposition`（含 UTF-8 中文文件名）、支持 Range
- html / svg / xml / js 一律按附件下载，防 XSS
- 看不到的文件 `download-url` 返回 404
- `DELETE /files/:key`：会话或表格里还引用着就只移出云盘，没人引用了才真正删除

**多维表格**
- `GET /tables` 每个字段都有 `title`（中文）、`options`、`option_colors`、`required`；每张表有 `name`、`description`、`icon`、`primary_field`
- 记录列表带 `total`（已扣除保密记录）、`created_by`、`updated_by`；支持 `keyword`
- 筛选条件写了不存在的字段或格式不对返回 422（以前内存版会静默返回空）
- 人员字段的 id 必须是存在的用户，附件字段的 file_key 必须存在且自己能访问，否则 422；附件会补上 `file_name`、`size`、`content_type`
- 筛选条件里的 `>=`、`<=` 以前会被误解析成 `>`、`<`（如 `budget>=1000` 查不到任何记录），已修好

**新建数据表 `POST /tables`（对应《多维表格新建数据表接口需求》）**
- 所有已登录、未禁用的用户都能建；成功 201，返回结构与 `GET /tables` 单项一致，另带 `builtin:false`、`created_by`、`created_at`、`updated_at`
- `key` 形如 `tbl_8f3a2c91d0`，创建后不变，直接用于现有 `/tables/:table_key/records` 五个接口
- 同一用户 24 小时内重复提交同一 `client_request_id`：返回 200 + 第一次建的表（并发重复提交也只建一张）
- 表名去空格后大小写不敏感地唯一，和内置表的中文名、英文名也不能重复，冲突返回 409 `TABLE_NAME_EXISTS`
- 参数错误 422 `VALIDATION_FAILED`，`errors[].field` 用 `name`、`primary_field`、`fields[1].field_name`、`fields[1].options[0]` 这类路径，message 是中文
- 和需求文档略有不同的两点：
  1. `field_name` 最长 63 个字符（PostgreSQL 列名上限；需求正则允许 64）。另外不能用系统保留名 `record_id`、`created_at`、`updated_at`、`created_by`、`updated_by`、`feishu_record_id`、`cos_created_by`、`cos_updated_by`
  2. 非单选 / 多选字段带了非空 `options` 返回 422（`options: []` 或 `null` 放行）
- 单选 / 多选可以带 `option_colors`（颜色名必须是前端调色板里的）；不带就按 blue、green、orange、red、purple… 顺序自动分配
- 新表的记录校验按建表时的定义：必填（新增时必须有，修改时不能清空，空数组也算清空）、类型、选项、人员 id、附件引用
- `GET /tables` 内置表在前，自定义表按创建时间正序；每项都带 `builtin`
- 存储：定义存在 `cos_custom_tables`；PostgreSQL 模式下每张新表会建一张同名物理表（列类型和内置表一致），启动时自动补建，重启后表和记录都在
- 暂不支持：改表结构 / 删表、关联字段（type 18）、按角色控制谁能建表（要只允许管理员建表，在 `routes-tables.ts` 的 `POST /api/v1/tables` 里加一行角色判断就行）

**云文档**
- `POST /docs` 直接返回完整 Doc（保留 `doc_id`、`url`），`markdown` 可省略
- Doc 带 `created_at`、`updated_by`、`can_edit`、`summary`（前 80 字）
- 列表按 `updated_at` 倒序，支持 `scope`、`keyword`、分页
- `PATCH` 带 `base_updated_at` 时做并发保护，冲突返回 409 + 最新 `doc`
- 文档内容按创建者可编辑处理；管理员可以删除但不能编辑

**协同编辑（回答文档 9.6 的三个问题）**
1. 正文共享类型：`Y.Text`，key = `"markdown"`
2. 非创建者连接是只读：能收到同步和别人的修改，发出的修改服务端丢弃
3. REST `PATCH markdown` 会清掉协同态，并以关闭码 4409 断开正在协同的连接（前端重连即可从新内容开始）；删除文档以 4404 断开

**日历 / 任务**
- 日程带 `created_at`、`updated_at`、`location`、`all_day`、`attendees[].rsvp`、`color`、`reminders`；创建者自动 `accepted`，其他人 `pending`
- `PATCH /calendar/events/:id` 仅创建者；`POST /calendar/events/:id/rsvp` 参与人回复
- `GET /calendar/events?user_id=` 查同事忙闲，只返回时间段
- 新建 / 新增参与人推送 `calendar.invited`；指派任务给别人推送 `task.assigned`
- 任务 `PATCH` 中 `null` 表示清空；可以改 `assignee_id`；变为 `done` 时写 `completed_at`，改回其他状态清空
- `DELETE /tasks/:id` 仅创建者（负责人 403）
- `GET /tasks` 支持 `assignee_id=me`、`created_by=me`

## 4. 二期迭代 1（《二期功能需求文档》R-BT-01 ~ 06、R-NT-01 / 02）

### 功能开关
- `GET /capabilities`（**不用登录**）→ `{ "features": { ... } }`。迭代 1 打开：`table.create`、`table.fields`、`table.views`、`table.realtime`、`table.batch`、`notifications`。之后各迭代打开的开关见 9、10、11 节；当前完整开关表见 **11.1**。缺失的 key 当 false。

### 数据表与字段（R-BT-01 / 02）
- `GET /tables`、`GET /tables/:key` 的表对象新增：`builtin`、`version`、`permissions { can_view, can_edit, can_comment, can_manage, can_delete }`、`view_ids`；每个字段新增 `builtin`、`description`。
- 权限（R-BT-09 上线前）：所有成员能看、能改记录；**管理员或自定义表的创建者**能管理字段；只有自定义表能删（删表接口还没做）。
- `POST /tables/:key/fields`：`{ field_name?, title, type, required?, options?, option_colors?, description?, after_field?, base_version? }`。不传 `field_name` 时后端生成 `field_1`、`field_2`……。返回 201 + 整张表。
- `PATCH /tables/:key/fields/:field`：可改 `title`、`type`、`required`、`description`、`options`、`option_colors`、`option_renames`（`{ 旧: 新 }`，已有记录同步改名）。删掉的选项在记录里清空。改类型时转不了的值清空。
- `POST /tables/:key/fields/:field/convert-preview` `{ type, options? }` → `{ affected, will_clear }`。
- `DELETE /tables/:key/fields/:field?base_version=`（**版本放在 query**）。
- `PUT /tables/:key/fields/order` `{ field_names }`：没列出的字段按原顺序接在后面。
- 所有字段接口都返回整张表的最新定义（`version` +1）。
- 错误码：`base_version` 不是最新 → 409 `VERSION_CONFLICT`（带 `table` 最新定义）；主字段删除 / 改类型 / 改成非必填 → 422；**内置字段**只能改名称和选项，其他改动 403；字段被视图的筛选 / 排序 / 分组 / 看板 / 日历引用时不能删 → 409 `FIELD_IN_USE`，`message` 写明「视图「xx」的分组」，`references` 列出全部视图。
- 内置表也可以加自定义字段；字段名不能和内置列（包括已改名的）重名。

### 视图（R-BT-03 / 04）
- `GET /tables/:key/views`：公共视图 + 自己的个人视图。一张表第一次访问时自动建一个公共「表格视图」（`vew_default_<表 key>`）。
- `POST /tables/:key/views` `{ name, type: grid|kanban|calendar|gantt|gallery, personal?, config? }`；没有编辑权限的人只能建个人视图。
- `PATCH /tables/:key/views/:view_id`：**必须带 `version`**，可改 `name`、`type`、`config`（整体替换）、`personal`。版本不对返回 409 `VERSION_CONFLICT` 并带最新 `view`。
- `DELETE`：最后一个公共视图不能删、也不能改成个人视图（422）。`PUT /tables/:key/views/order` `{ view_ids }`。
- `config` 原样保存（包括前端自己加的 key）。后端只检查引用的字段存在、运算符合法。
- `GET /tables/:key/records?view_id=` 由后端按视图筛选、排序；有分组时：先按分组字段排序，返回 `groups: [{ path, count }]`（每层都有）；`&group_path=["借出"]` 只取这一组。
- 筛选规则和前端 `view_engine.dart` 一致：`is` 的值是字符串数组；日期按天比较；`today` / `this_week`（周一开始）/ `last_7_days` 等按**北京时间**算（环境变量 `CLASSMATE_OS_TZ_OFFSET_MINUTES` 可改）；值为空的条件不生效；排序时空值排在最后。

### 批量操作（R-BT-06）
- `POST /tables/:key/records/batch_create` `{ records: [{ fields }] }`
- `POST /tables/:key/records/batch_update` `{ records: [{ record_id, fields }] }` 或 `{ record_ids, fields }`（统一修改）
- `POST /tables/:key/records/batch_delete` `{ record_ids }` 或 `{ view_id, all: true }`（删视图里的全部，最多 1 万条）
- 一次最多 500 条。返回 `{ succeeded, failed }`，单条失败不影响其他条；`failed[].message` 是中文原因，例如「「状态」必须是以下之一：空闲、借出」。

### 实时刷新（R-BT-05）
- 用户 WS 新增客户端消息 `{ "type": "subscribe" | "unsubscribe", "topic": "table:<key>" }`，后端回 `subscribed` / `unsubscribed`，失败时回 `subscribe_failed`（`code`：`NOT_FOUND` / `INVALID_TOPIC` / `TOO_MANY_TOPICS`）。每个连接最多 50 个主题。**重连后要重新订阅。**
- 订阅后能收到：`record.changed { table_key, action, record_id, operator_id, record?, changed_fields? }`、`table.schema_changed { table_key, version }`、`table.view_changed { table_key, view_id, action }`。`table.created` / `table.deleted` 不用订阅。
- 前端可以用 `operator_id` 忽略自己操作触发的事件。
- 保密记录（`projects` 表 `visibility=保密`）只推给负责人和管理员；从公开改成保密时，其他人收到 `action: deleted`。
- 断线带 `since` 重连后，**第一次订阅**某个主题时会补发 `since` 之后这个主题的事件。
- 连 WS 时可带 `&platform=macos|windows|linux|web|ios|android`，用于「桌面端在线时手机不推送」。
- 这些界面事件不会发给机器人（大脑 WS）。

### 通知中心（R-NT-01）
- `GET /notifications?filter=all|mention&page_size=&page_token=`（倒序，额外带 `unread_count`）、`GET /notifications/unread-count` → `{ count }`、`POST /notifications/read` `{ ids }` 或 `{ all: true }` → `{ updated, count }`。
- 已经接上的通知来源：任务指派（`task.assigned`）、日程邀请（`calendar.invited`）、任务 24 小时内到期（`task.due_soon`，每 5 分钟扫一次，每个任务的同一个截止时间只提醒一次）。文档评论、审批等等对应模块上线时再接入。
- WS：`notification.new { notification }`（完整对象）、`notification.read { count }`（同一账号多端同步角标）。

### 通知设置与推送（R-NT-02）
- `GET/PUT /users/me/notification-settings`，结构同需求文档；PUT 可以只传要改的部分，`dnd.start/end` 格式 `HH:MM`。
- 设备注册 `POST /devices` 的 `platform` 新增 `macos`。
- 推送规则（消息和通知共用）：总开关 → 分类开关（被 @ 走「@我」分类）→ 免打扰时段（北京时间，可跨午夜）→ 桌面端在线时不推（手机按开关，macOS 设备本身在线时也不推）→ 关闭「显示内容」时正文换成「张晓明 发来一条新消息」。会话设了免打扰的普通消息不推。
- **真实送达还需要 APNs / FCM 证书**。现在默认用内存推送（只记录不发送），配好证书后实现 `PushProvider` 接口即可。

## 5. 和以前行为不同的地方

- 默认种子账号 id 仍是 `ou_admin` / `ou_demo`，登录名 `admin` / `demo` 不变
- 建会话时成员必须是存在的用户（以前随便填也能建）
- 用户 WS 除 `message.receive` 外还会收到 chat.* / message.updated / message.read 等事件，前端不认识的事件请忽略
- 机器人账号 `bot`（显示名「飞书同学」）会出现在成员列表里，方便前端翻译名字；它不能登录
- 内置表 GET 返回多了 `builtin`、`version`、`permissions`、`view_ids` 等字段，不影响原有字段
- 记录列表排序相同时，按创建时间、记录 ID 兜底，保证翻页不重不漏
- 旧测试已按新行为更新：`pg-store.test.ts`（SQL 带 total、数字按数值比较）、`user-ws.test.ts`、`bot-events.test.ts`、`bot-gateway.test.ts`（补测试账号）、`collab.test.ts`（非创建者只读）

### 8.5 文档权限申请与所有者转移（`doc.permissions` 已于 2026-10-20 打开）

- `POST /api/v1/docs/:doc_id/transfer` `{ owner_id }`：只有当前所有者可以转移。新所有者必须是有效成员；原所有者会自动保留「可管理」权限。保存时检查权限版本，并发冲突返回 409 `VERSION_CONFLICT`。
- `POST /api/v1/docs/:doc_id/access-requests` `{ role, note? }`：`role` 只能是 `viewer`、`commenter`、`editor`，备注最多 2000 字。返回 201 和申请对象。同一用户对同一文档只能有一条待处理申请，重复提交返回 409 `ACCESS_REQUEST_PENDING`；已有同等或更高权限时返回 409 `ACCESS_ALREADY_GRANTED`。
- 申请通知发给所有者：`type: "doc.access_request"`，`target: { type: "access_request", doc_id, request_id }`。
- `POST /api/v1/docs/:doc_id/access-requests/:request_id/approve|reject`：只有所有者可以处理。处理结果会通知申请人。同意时只会升级权限，不会降低已有权限。申请状态和权限版本在同一步检查：已处理或并发处理时，只有一个请求成功，其余返回 409 `VERSION_CONFLICT`。
- 保存分享设置、转移所有者、同意申请后，都会断开当前协同连接（关闭码 `4410`）。同时给修改前或修改后有权访问的用户推送 `doc.permission_changed { doc_id, user_ids: [] }`，`user_ids` 为空表示相关用户都要重新拉取文档。事件只包含文档 ID，不含正文。
- PostgreSQL 新增 `cos_doc_access_requests`，用唯一部分索引保证同一用户、同一文档只有一条待处理申请。

本轮验证：`tests/classmateos/doc-permissions.test.ts` 2 个测试通过，覆盖越权处理、重复申请、并发审批、审批后可编辑和所有者转移；后端严格 TypeScript 检查通过。仍未在真实 PostgreSQL 上运行。

### 8.6 文档评论、历史版本、图片和附件（`doc.comments`、`doc.versions` 已于 2026-10-20 打开）

**评论（R-DC-02）**
- `GET /docs/:doc_id/comments?solved=true|false`：需要查看权限，按创建时间正序分页。每项包含 `comment_id`、`doc_id`、`quote`、`anchor`、`is_whole`、`solved`、`replies[]`、`created_by`、`created_at`、`updated_at`、`quote_deleted`。原文在正文里找不到时，`quote_deleted` 为 true。
- `POST /docs/:doc_id/comments` `{ is_whole, quote?, anchor?, content }`：需要 `can_comment`，也就是「可评论」及以上。划词评论必须带 `quote`，`anchor` 原样保存、不检查格式（对应前端约定 3.2）。`content` 采用 2.4 的 `{ text, mentions }` 结构，正文最多 5000 字。返回 201，第一条回复已包含在 `replies` 里。
- `POST .../comments/:comment_id/replies` 新增回复，返回回复对象；新回复会把已解决的评论重新打开。`PATCH` 和 `DELETE .../replies/:reply_id` 只能修改或删除自己的回复，否则返回 403。最后一条回复被删除后，整条评论也会删除。
- `PATCH .../comments/:comment_id` `{ solved }`：解决或重新打开评论。
- 评论修改采用版本检查，并发写入会自动重试；仍然冲突时返回 409 `VERSION_CONFLICT`。
- 通知：被 @ 且能看文档的人收到 `doc.mention`；文档所有者和评论发起人收到 `doc.comment`，不会通知操作者本人。`target` 为 `{ type: "doc", id, doc_id, comment_id }`。
- WS：主题 `doc:<doc_id>` 推送 `doc.comment_changed { doc_id, comment_id, action }`，`action` 可能是 `created`、`updated`、`deleted`、`solved`、`reopened`。

**历史版本（R-DC-03）**
- 自动保存版本的时机：创建文档时、距上一版超过 30 分钟时、停止编辑 2 分钟后（REST 保存和协同编辑都会计时）、还原前后。内容和上一版相同时不保存新版本。
- `GET /docs/:doc_id/versions`：按时间倒序，每项包含 `version_id`、`name`、`created_by`、`created_at`、`added`、`removed`。增删字数按前后缀对齐估算。
- `GET .../versions/:version_id` 返回上面的字段，另加 `title` 和 `markdown`。
- `PATCH .../versions/:version_id` `{ name }` 用于命名版本，名称最多 50 字；传 `null` 或空字符串表示清除名称。需要 `can_edit`。
- `POST .../versions/:version_id/restore` 需要 `can_edit`。还原前会先保存当前内容，还原后再生成一个新版本，并用 `4409` 断开协同连接。返回 `{ doc_id, updated_at, version }`。
- 协同编辑保存的版本不知道具体是谁改的，`created_by` 记录为文档最后一个通过 REST 保存的人。版本暂时不会自动清理。

**图片和附件（R-DC-04）**
- `POST /files/upload-url` 新增可选参数 `ref: { type: "doc", id }`，需要该文档的编辑权限，否则返回 403。文件会直接绑定到这篇文档。
- 保存正文时，后端会识别 `cos-file://file_key`：对当前用户自己能访问的文件，也会自动绑定到这篇文档。这样复制、粘贴已有图片时也能正常分享。
- 能查看文档的人，就能获取文档里绑定文件的 `download-url`；其他人返回 404。签名地址有效期仍为 1 小时。
- 文档删除后清理图片，要等回收站做完再接入（见 8.3）。

**存储**：PostgreSQL 新增通用对象表 `cos_entities(kind, id, scope, data, version, …)`，评论（`doc_comment`）、版本（`doc_version`）、附件绑定（`doc_file`）都存在这里。修改时用 `version` 防止并发覆盖。

### 9.4 重复日程（2026-10-20 加固完成，`calendar.recurrence:true`）

- 列表兼容 from/to 和 start_ms/end_ms，查询窗最多一年。
- 创建支持 recurrence；PATCH/DELETE 支持 query scope=this|following|all。实例 ID 不透明，必须使用响应中的 ID。
- 保存 this 时可原样回传相同规则，不允许更换规则。following/all 的时间按正在编辑的实例计算偏移。
- recurrence 省略不改，null 取消；all 取消只保留当前编辑实例。following 拆分系列；变更规则会清掉受影响部分的例外实例。
- **时区**：日程可带 IANA `timezone`（如 `America/New_York`），重复规则按该时区的本地时间展开，跨夏令时仍是本地同一时刻；夏令时跳过的本地时间往后顺延。不带时用服务器默认日历时区（参数 > 环境变量 `COS_CALENDAR_TZ` > `Asia/Shanghai`），响应里总会带上实际使用的 `timezone`。传 `null` / 空串清除；非法时区返回 422。
- **全天日程**按本地 0 点展开；跨年、闰日（2/29 的每年规则只在闰年出现）都有测试。
- **远期日期**：不再有 5000 次累计上限，十几年后的实例照常能查到。
- **例外实例跨出原时间窗**：单独把某一次挪到别的日期后，原窗口不再出现、新窗口能查到。
- **原子写入**：拆分系列 / 单独改某一次涉及的多条写入在同一个数据库事务里，中途出错整批回滚；提交时校验主日程版本，别人刚改过时返回 `409 EVENT_CONFLICT`，前端重新拉取后再试。
- **通知**：日程类通知（邀请、变更、提醒）的 `target` 带 `start_ms`（v0.4 约定），重复日程是对应那一次的开始时间。
- 支持 DAILY/WEEKLY/MONTHLY/YEARLY、INTERVAL、COUNT、UNTIL、常用 BYDAY/BYMONTHDAY/BYMONTH；不是完整 RFC 5545。不能识别的规则返回 422，不会静默保存。
- RSVP：前端日历卡片按钮还没做，后端沿用现有日程接口，前端做好后再联调。

## 10. 前端迭代 4 适配（2026-10-20，对照《二期迭代4_前端接口需求与进度.md》）

已打开的开关：`message.thread`、`message.reaction`、`message.forward`、`message.urgent`、`message.favorite`、`message.pin`、`message.link_preview`、`message.rich_text`、`search`。`wiki` 仍为 false。

### 10.1 已读回执（R-IM-01）

- 自己发的消息带 `member_count`（除自己和机器人外的成员数）和 `read_count`（准确人数）。别人发的消息不带这两个字段。
- `GET /messages/:message_id/read-users` → `{ read: [user_id], unread: [user_id] }`，只有发送人能看，其他人 403。
- `POST /chats/:chat_id/read` 之后，`message.read` 事件推给会话里**所有成员**（发送人据此刷新已读数）。

### 10.2 话题（R-IM-02）

- 发话题回复：`POST /chats/:chat_id/messages` 带 `thread_root_id`；`also_send_to_chat:true` 时同时出现在群消息流里。不带 `also_send_to_chat` 的回复只在话题里，不出现在会话消息列表、不计入会话未读。
- 不能在话题回复里再开话题（422）；撤回的消息、系统消息不能当话题根。
- 根消息带 `thread: { reply_count, last_reply_at, participants, followed }`。
- `GET /messages/:message_id/thread?page_size=&page_token=` 按时间正序分页；打开即把看到的回复记为已读。
- 关注：`POST / DELETE /messages/:message_id/thread/follow`。发起人和回复人自动关注。
- 会话带 `thread_mode`、`thread_unread_count`（我关注的话题里有新回复的个数）。`PATCH /chats/:chat_id { thread_mode }` 切换话题模式。

### 10.3 表情回应（R-IM-03）

- `POST /messages/:message_id/reactions { emoji }`、`DELETE /messages/:message_id/reactions/:emoji`。emoji 是 1～32 位字母数字下划线的 key（如 `thumbsup`），重复添加幂等。
- 消息带 `reactions: [{ emoji, count, user_ids, reacted_by_me }]`；变化时推 `message.updated`。撤回后不显示回应。
- 每条消息最多 50 种表情；每人每分钟 60 次，超过 429 `RATE_LIMITED`。

### 10.4 转发（R-IM-04）

- `POST /messages/forward { message_ids, chat_ids, mode: single|merge, note?, client_request_id? }`，返回 201 `{ items: [新消息] }`。
- 最多 100 条消息、10 个会话；源消息和目标会话都必须是自己能看到的，否则 422 并指出第几项。撤回、卡片、系统消息不能转发。
- `single` 逐条转发，新消息带 `forwarded_from: { chat_id, chat_name, sender_id, message_id }`；`merge` 生成一条 `merge_forward`，`content: { title, messages: [快照] }`，标题是「xx的聊天记录」。
- 同一个 `client_request_id` 只执行一次：重复提交返回 200 和第一次的结果；第一次还在处理时返回 409 `REQUEST_IN_PROGRESS`。
- 转发出去的图片 / 文件（含合并转发里嵌套的）对目标会话成员可下载。

### 10.5 加急（R-IM-05）

- `POST /messages/:message_id/urgent { user_ids, type: app|push }`：只能加急自己发的消息、对象必须是会话成员。被加急的人收到 `message.urgent` 事件；`type:push` 时同时生成通知。
- 每人每条只能加急一次；每人每分钟最多 10 次。超过都返回 429 `URGENT_TOO_FREQUENT`。
- `GET /messages/urgent/pending` → 我还没确认的加急（`message_id, chat_id, from_user_id, preview, urged_at`）。
- `POST /messages/:message_id/urgent/ack` → 204，推 `message.urgent_acked { message_id, user_id }` 给自己（多端同步）和发送人。发送人看到的消息带 `urgent: { user_ids, ack_user_ids }`。

### 10.6 收藏和 Pin（R-IM-06）

- 收藏：`POST / DELETE /messages/:message_id/favorite`（204，幂等）；`GET /favorites?page_size=&page_token=` → `{ items: [{ favorite_id, message, chat_name, created_at }], has_more, page_token? }`。消息撤回或自己退群后列表里不再返回；退群后仍可取消收藏。
- Pin：`GET /chats/:chat_id/pins`、`POST / DELETE /chats/:chat_id/pins/:message_id`。每个会话最多 10 条，超过 409 `PIN_LIMIT`。固定时会发一条系统消息，并推 `chat.updated`（带 `pinned_message_ids`）。会话对象也带 `pinned_message_ids`。

### 10.7 富文本、链接预览、单条记录（R-IM-07）

- `post` 消息支持 `content.markdown`（最多 2 万字），也兼容原来的 `title / text`。`text` 消息支持 `content.mentions: [{ user_id, name }]`。
- 链接预览由后端生成：发送后异步抓取外部链接（每条最多 3 个），写回 `content.link_previews: [{ url, title, description }]` 并推 `message.updated`。前端传来的 `link_previews` 会被忽略。指向本应用的内部链接不抓取。
- 防内网访问：只允许 http/https 和 80/443 端口；拒绝带账号密码的网址、localhost、内网 / 回环 / 链路本地 / 云元数据等地址；域名解析出的地址都要是公网，并且实际连接检查过的那个地址；跳转每一跳都重新检查，最多 3 跳；5 秒超时、最多读 512 KB、只解析网页。
- 频率：每人每分钟 20 个链接；同一网址成功结果缓存 1 小时、失败缓存 10 分钟。
- 单条记录：`GET /tables/:table_key/records/:record_id`，权限和列表一致（保密记录对无权的人 404）。

### 10.8 全局搜索和最近访问（R-SR-01）

- `GET /search?q=&types=&page_size=&page_token=` → `{ groups: [{ type, total, items: [{ id, title, snippet, updated_at, extra }], page_token? }] }`。
  - `types` 可选 `user, chat, message, doc, wiki, record, task, event`，逗号分隔；不传时返回除 wiki 外的 7 类。未知类型 422。
  - 多个类型时每组默认 3 条；只搜一类时默认 20 条，最多 50 条，`page_token` 只在单类型时生效（不透明字符串，原样回传）。
  - 筛选：`chat_id`、`sender_id`（消息）；`owner_id`（文档）；`start_ms`（消息发送时间 / 文档更新时间不早于）；`table_key`（记录）。
  - 匹配：不区分大小写的子串匹配，中文不需要分词，空格分隔的多个词都要出现（最多 5 个词，关键词最多 100 字）。空关键词 400。
  - 高亮只用 `<em>…</em>`，原文里的 em 标签会被去掉。`title` 带高亮；`snippet` 是命中附近的片段（记录是「字段名：片段」）。
  - 所有结果都按权限过滤，`total` 是过滤后的准确数：只搜我所在的会话的消息、我能看的文档（私密文档对外人不可见）、我有权看的记录（保密记录）、我相关的任务和日程。单聊不出现在 chat 分组里，通过 user 分组找人。
  - `extra`：message 带 `chat_id / sender_id / thread_root_id`；doc 带 `owner_id`；record 带 `table_key / table_name`；task 带 `status / due_ms / parent_id`；event 带 `start_ms / end_ms / all_day / recurring_event_id`（重复日程定位到下一次）；user 带 `department`；chat 带 `member_count`。
  - wiki：Wiki 还没实现，请求 `types=wiki` 返回空分组。
- `GET /recent?page_size=`（默认 10，最多 50）→ `{ items: [{ type: doc|table|record, id, title, visited_at, extra }] }`。打开文档详情、表格、单条记录（GET 返回 200）时自动记录，最新在前，每人保留 100 条。返回前重新检查权限、刷新标题，没有权限或已删除的不返回。
- 性能（PostgreSQL 16.2，本机，1 万条消息 + 1000 篇文档 + 20 个群）：综合搜索中位 17～19 毫秒，只搜消息 17～18 毫秒，只搜文档 11 毫秒，最慢一次 22 毫秒，满足 500 毫秒要求。数据库有 `pg_trgm` 扩展时会自动建 trigram 索引；没有权限装扩展时跳过，功能不受影响但大数据量会变慢。

### 11.2 `capabilities.web_url` 与 `user.permissions`

### 11.3 协同在线头像（`doc.presence`）

回答总览第 4 节第 5 问：**协同 WS 允许只读用户连接**。只读连接发来的正文修改会被丢弃，awareness（类型 1）照常转发。前端按迭代 2 文档 3.6 的格式发 `{user_id, name, color, cursor: {line}}` 即可。后端额外做了三件事：

- **防冒充**：转发前把每条状态里的 `user_id`、`name` 改写成这个连接登录的本人。前端显示别人头像时，信这两个字段就行。
- **不能抢别人的 clientID**：同一房间里另一个连接已经用过的 clientID，这个连接不能再发，整条消息丢弃。
- **断开时替他广播离开**：连接断开后，后端给房间里其他人发一条该 clientID 的 `null` 状态（clock + 1），头像立刻消失，不用等 35 秒过期。

单条 awareness 超过 16 KB、一条里超过 64 项，或格式错误时，整条丢弃。

**请前端留意**：现在 `collab_presence.dart` 收到 4410（权限被收回）后 1 秒就重连。如果是被取消了查看权限，重连会马上再被 4410 断开，变成每秒重连一次。建议收到 4410 后先调 `GET /docs/:id` 确认：返回 403 / 404 就停止重连。

### 11.6 批次 1：「我的」页与安全设置（`auth.password`、`auth.sessions` 已打开）

**登录设备会话**
- 每次登录生成一个设备会话，登录 / 刷新返回新增 `session_id`、`must_change_password`（`user` 里也带）。access / refresh 令牌都带会话 ID，刷新时会话 ID 不变。
- **请前端在 `POST /auth/login` 的请求体里带 `device_name`、`platform`**（`macos|windows|linux|web|ios|android`），也可以用请求头 `X-Device-Name`（中文需 URL 编码）/ `X-Platform`。没带时按 User-Agent 猜，猜不出显示「未知设备」。现在前端登录没带，设备列表会多是「未知设备」。
- `GET /users/me/sessions` → `{items:[{session_id, device_name, platform, ip, last_active_at, created_at, current}], total, page_token:null, has_more:false}`，最近活跃在前。`last_active_at` 每分钟最多更新一次。
- `DELETE /users/me/sessions/:session_id` → 204；不是自己的或已退出 → 404。可以踢掉当前设备（相当于退出登录）。
- `POST /users/me/logout-all` → `{revoked: N}`，**按需求文档保留当前设备**。前端 `phase2_admin.dart` 里 `logoutAllMine` 的注释写的是「含当前」，两边不一致：要退出当前设备，再调一次 `POST /auth/logout` 即可。
- 被踢、改密、管理员重置密码 / 强制下线 / 停用后：该会话的接口返回 401（`code`：`SESSION_REVOKED`；空闲超时为 `SESSION_IDLE_TIMEOUT`），refresh 返回 401 `REFRESH_EXPIRED`，正在连接的用户 WS、协同 WS 以 **4401** 关闭。前端统一按「登录已过期」处理即可。
- 升级前签发的旧令牌（没有会话 ID）仍可使用；用旧 refresh 刷新时自动补建一个会话。账号做过「退出全部设备 / 改密 / 停用」后，旧令牌一律失效。
- 多实例部署时，其他实例最多 3 秒后才发现会话被吊销（本实例立即生效）。

**改密码** `POST /users/me/password {old_password, new_password}` → 204
- 旧密码错 → 400 `INVALID_PASSWORD`「当前密码不正确」；不满足规则 → 400 `WEAK_PASSWORD`，`message` 如「密码至少 8 位，且必须同时包含字母和数字」；新旧相同也是 `WEAK_PASSWORD`。
- 成功后其他设备立即失效，当前设备保留（当前 refresh 也能继续用），并清除强制改密标记。

**头像** `PATCH /users/me {avatar_file_key}`：文件必须已上传、本人能访问、类型是 png / jpeg / gif / webp；传 `null` 清除。后端返回完整网址的 `avatar_url`，形如 `https://host/api/v1/users/<id>/avatar?v=...`（**公开地址，不需要令牌**，因为图片组件带不了令牌）。网址前缀取环境变量 `CLASSMATE_OS_PUBLIC_URL`，没配置时按请求的 Host / `X-Forwarded-*` 推出，部署在反向代理后面时建议配置。注意：头像文件被从云盘删除后头像会失效。

| 字段 | 默认 | 允许范围 |

| `idle_timeout_minutes` | 0（不启用） | 0 或 5～43200 |

校验失败 422，`message` 是第一条中文原因，`errors` 列出全部。

- **失败锁定**：同一账号连续输错达到次数后锁定，返回 **423** `ACCOUNT_LOCKED`「登录失败次数过多，账号已锁定，请 N 分钟后再试」（带 `retry_after_minutes`），锁定期间密码正确也是 423。普通输错仍是 401 `invalid credentials`。登录成功后次数清零。请前端把 423 的 `message` 直接展示。

### 12.3 B3 确认卡片绑定操作、只能用一次

- 确认卡片（`kind=confirm`）内容新增 `bound_action: { method, route, path?, target_id? }`：`route` 是带 `/api/v1` 的路由模板，`target_id` 是对象 id，批量删除时是 id 数组。格式不对发卡返回 422。
- 带 `X-Agent-Confirm` 代办删除时，服务端核对：方法一致；路由模板或实际路径一致；对象一致（批量删除取 body 里的 `record_ids` / `ids` / `file_keys`，否则取路由最后一个参数，按集合比对）。规则和 agent 的 `boundActionOf` 一致。
  - 对不上，或卡片没带 `bound_action` → **403 `BOT_CONFIRM_MISMATCH`**
  - 用过的卡再用 → **409 `CARD_CONSUMED`**
- 「只用一次」靠 `cos_entities` 里的 `confirm_card_use` 记录（不存在才插入，PG 下是 `ON CONFLICT DO NOTHING`），并发也只会成功一次；卡片消息上同时写 `consumed_at`。同一个请求里鉴权走两次不算重复使用。
- 没带 `bound_action` 的确认卡片（如机器人物理动作的确认）照常可以发，只是不能用来放行服务端删除接口。
