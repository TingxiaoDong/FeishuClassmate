## 2. 通用约定

- 以下路径相对于 `/api/v1`。
- 认证、令牌刷新、错误处理复用现有 `CosApiClient.request`。
- 列表建议统一返回 `{items, has_more, page_token}`；下一页字段最终需与现有 `CosPage` 解析核对。不得只加载第一页后声称已加载全部。
- 时间戳字段使用毫秒整数；`created_at`、`updated_at` 使用 ISO 8601。
- 所有按钮依赖服务端 `permissions`；不以管理员/创建者身份推测二期权限。
- 富文本沿用 `{text, mentions:[{user_id,name,offset,length}]}`。
- 写请求失败时保留输入，显示错误，不能提前展示成功状态。
- 409 并发或状态冲突需重新拉取数据，保留尚未提交的表单草稿。

## 3. 重复日程

### 3.1 日程新增字段（原需求已定义）

```json
{
  "recurrence": "FREQ=WEEKLY;BYDAY=MO",
  "recurring_event_id": "evt_series",
  "original_start_ms": 1792375200000,
  "is_exception": false
}
```

- `recurrence`：RFC 5545 RRULE；不重复为 null。
- `recurring_event_id`：系列标识；实例 ID 是不透明字符串，前端不自行按下划线拆解。
- `original_start_ms`：实例最初的开始时间，修改例外实例后仍保持原值。
- `is_exception`：是否为单独修改的实例。
- 服务端在查询时间窗内展开实例，前端不自行展开正式数据。

### 3.2 接口

| 方法 | 路径 | 约定 |
|---|---|---|
| GET | `/calendar/events?start_ms=&end_ms=` | 时间窗内展开后的实例 |
| POST | `/calendar/events` | 原有请求体增加 `recurrence` |
| PATCH | `/calendar/events/:event_id?scope=this\|following\|all` | 修改指定范围 |
| DELETE | `/calendar/events/:event_id?scope=this\|following\|all` | 删除指定范围 |

**兼容差异：当前前端 `listEvents` 传的是 `from/to`，新需求写 `start_ms/end_ms`。** 新实现需按功能开关区分或由后端兼容两套参数，不能直接破坏一期接口。

### 3.3 编辑器和前端行为（v0.4 补齐）

- 「重复」下拉：不重复 / 每天 / 每个工作日 / 每周（当天星期几）/ 每两周 / 每月（按日期）/ 每月（第几个星期几）/ 每年 / **自定义…**。
- 自定义弹窗：每 N 天 / 周 / 月 / 年；按周时可多选星期几；按月时选「按日期」或「第几个星期几」（含「最后一个」，即 `BYDAY=-1MO`）。
- 结束条件：**永不 / 到某天（`UNTIL`）/ 重复 N 次（`COUNT`）**，两者互斥。`UNTIL` 由前端按所选那天的本地 23:59:59 转成 UTC，格式 `YYYYMMDDTHHMMSSZ`。
- 前端能解析的 RRULE 子集：`FREQ`（DAILY / WEEKLY / MONTHLY / YEARLY）、`INTERVAL`、`BYDAY`（含序号）、`BYMONTHDAY`、`COUNT`、`UNTIL`。超出这个子集的规则（如 `BYSETPOS`、`BYHOUR`）显示「保留现有自定义规则」，原样保存。
- 详情面板显示规则的中文描述，如「每 2 周的周一、周三，共 10 次」。
- **只在规则真的变了时才发 `recurrence`**；选了「仅此日程」时**不发** `recurrence`（单个实例不能改重复规则，前端也把「重复」下拉禁用）。
- 选了「仅此日程」以外的范围时，前端提示「之前的日程不受影响」/「所有日程都会改」。
- 例外实例（`is_exception: true`）修改时不提供「此日程及之后」（只能改这一次或全部）。
- 前端**不自行展开正式数据**；测试数据模式的展开逻辑（`services/rrule.dart`、`mock/mock_calendar.dart`）只用于自测，后端可对照。
- 从通知 / 搜索打开日程：`{type: "calendar", id, start_ms}`，日历翻到那一周并打开详情。**请在日程类通知的 `target` 里带 `start_ms`**，否则前端不知道翻到哪一周。

### 3.4 需要确认

1. 取消重复：建议显式发送 `recurrence:null`；省略表示不修改。
2. 范围字段放查询参数；`this` 修改开始时间时以实例 ID/原始开始时间定位，不能重新根据新时间匹配。
3. `following/all` 的开始结束时间代表“当前实例的新时间”还是“系列首例时间”？建议由后端根据当前实例计算偏移，前端不回推首例。
4. RRULE 的本地时区及 DST：建议日程补 `timezone`（IANA 时区），或明确服务器采用的日历时区。不能把本地每天固定时间当作固定 24 小时毫秒间隔。
5. 每月 29/30/31 日及第 5 个星期几不存在时建议遵循 RFC：跳过该月，不自动挪到月底。
6. `UNTIL` 为包含边界，按用户所选截止日转换；`COUNT` 与 `UNTIL` 互斥。
7. 无法识别的已有自定义 RRULE 必须原样保留并显示提示，不得保存时静默丢弃。
8. 单例删除、例外跨出原时间窗、系列拆分、跨年、全天日程均须纳入联调。

## 4. 任务扩展（前端已完成）

### 4.1 任务对象新增字段

```json
{
  "task_id": "task_1",
  "parent_id": null,
  "depth": 1,
  "subtask_count": 3,
  "subtask_done_count": 1,
  "follower_ids": ["ou_admin"],
  "tasklists": [{"list_id": "tl_1", "section_id": "sec_2", "name": "机械臂抓取项目"}],
  "permissions": {
    "can_view": true, "can_edit": true, "can_delete": false,
    "can_comment": true, "can_follow": true, "can_manage_followers": true
  }
}
```

| 字段 | 前端用途 | 缺失时前端的处理 |
|---|---|---|
| `parent_id` | 区分子任务；子任务详情不显示「所属清单」 | 当作顶层任务 |
| `depth` | 顶层为 1，`depth >= 3` 时不显示「添加子任务」 | 有 `parent_id` 记 2，否则 1 |
| `subtask_count` / `subtask_done_count` | 列表和清单卡片上的「1/3」进度 | 0，不显示进度 |
| `follower_ids` | 关注人头像、「关注 / 取消关注」、「我关注的」筛选 | 空 |
| `tasklists` | 详情「所属清单」，以及清单视图里按 `section_id` 分组 | 空 |
| `permissions` | 按钮显隐，见 4.6 | 退回一期规则：创建人和负责人可改，创建人可删 |

**`tasklists[].name` 请带上**：任务详情会显示它属于哪个清单，前端拿不到名字时只能再查一次清单列表。

### 4.2 子任务（R-TK-01）

| 方法 | 路径 | 前端实际发送 / 期望返回 |
|---|---|---|
| GET | `/tasks` | 默认**只返回顶层任务**；前端暂不传 `include_subtasks` |
| POST | `/tasks` | `{title, parent_id, assignee_id, due_ms?}`，返回新任务 |
| GET | `/tasks/:task_id` | **新增**。返回单个任务，前端在子任务 / 关注人 / 清单变化后用它刷新详情 |
| GET | `/tasks/:task_id/subtasks` | `{items, has_more, page_token}`，**按保存的顺序**返回 |
| POST | `/tasks/:task_id/subtasks/order` | `{task_ids: [...]}`，同一父任务下的全部子任务，新顺序 |

- 超过 3 层：请返回 422，`code: "TASK_DEPTH_EXCEEDED"`，`message` 用中文（前端直接显示）。
- 子任务的修改、完成、删除都用已有的 `PATCH / DELETE /tasks/:task_id`。修改子任务后请同时让父任务的 `subtask_done_count` 变化（前端会重新拉父任务）。
- **请后端确定**：删除父任务时子任务怎么处理。模拟后端目前是一起删除；完成父任务时**不会**自动完成子任务，前端也不会自动批量操作。

### 4.3 关注人（R-TK-02）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/tasks/:task_id/followers/:user_id` | 添加关注人（自己关注时 `user_id` 是自己） |
| DELETE | `/tasks/:task_id/followers/:user_id` | 移除 / 取消关注 |
| GET | `/tasks?follower_id=me` | 左栏「我关注的」 |

- 添加多人时前端逐个调用 POST。返回值前端不依赖，之后会重新 GET 任务。
- 关注人能看任务、能评论，不能改；前端在只读时提示「你是关注人，可以查看和评论，不能修改」。
- `can_follow`：能不能自己关注；`can_manage_followers`：能不能添加 / 移除别人。

### 4.4 评论和动态（R-TK-03）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/tasks/:task_id/comments` | 按时间正序 |
| POST | `/tasks/:task_id/comments` | `{content: {text, mentions}, attachments: [{file_key, name, size, mime_type?}]}`；文字和附件至少有一样 |
| DELETE | `/tasks/:task_id/comments/:comment_id` | 删除 |
| GET | `/tasks/:task_id/activities` | **按时间倒序**（最新在前） |

评论返回：

```json
{ "comment_id": "tc_1", "user_id": "ou_demo",
  "content": {"text": "@张晓明 图做好了吗", "mentions": [{"user_id": "ou_zhang", "name": "张晓明", "offset": 0, "length": 4}]},
  "attachments": [{"file_key": "file_1", "name": "结果.png", "size": 1024, "mime_type": "image/png"}],
  "created_at": "2026-10-19T14:00:00Z",
  "permissions": {"can_delete": true} }
```

- 附件上传复用一期 `POST /files/upload-url`，前端多传 `ref: {type: "task", id: task_id}`。**请后端允许 `task` 这种引用类型**，能看任务的人就能下载附件。单个附件前端限制 20 MB。
- 图片附件（`mime_type` 是 `image/*` 或扩展名是图片）直接显示缩略图，其余显示附件卡片。
- 被 @ 的人请发 `task.mention` 通知，`target: {type: "task", id: task_id}`。
- 没有 `permissions.can_delete` 时，前端只让作者删除自己的评论。

动态返回（前端按结构自己拼中文，**不要只给拼好的句子**）：

```json
{ "activity_id": "ta_2", "operator_id": "ou_demo", "at": "2026-10-19T02:00:00Z",
  "action": "updated",
  "changes": [{"field_name": "status", "before": "pending", "after": "in_progress"}] }
```

- 前端认识的 `field_name`：`title / status / assignee_id / due_ms / description / priority / follower_ids / tasklists`，显示为「李同学 把状态从「待开始」改为「进行中」」。其他字段名会原样显示。
- `changes` 为空时按 `action` 显示：`created / completed / reopened / subtask_added / follower_added / follower_removed / commented / tasklist_added / tasklist_removed`。

### 4.5 任务清单（R-TK-04）

| 方法 | 路径 | 前端实际发送 |
|---|---|---|
| GET | `/tasklists` | 我能看到的清单（没权限的不要返回） |
| POST | `/tasklists` | `{name, description?}` |
| PATCH | `/tasklists/:list_id` | `{name}` 或 `{description}` |
| DELETE | `/tasklists/:list_id` | 删除清单 |
| GET / PUT | `/tasklists/:list_id/members` | PUT 发 `{members: [{member_type: "user", member_id, role: "editor"\|"viewer"}]}`；GET 返回 `{owner_id, members}` |
| GET | `/tasklists/:list_id/sections` | 按 `order` 返回分组 |
| POST | `/tasklists/:list_id/sections` | `{name}` |
| PATCH | `/tasklists/:list_id/sections/:section_id` | `{name}` |
| DELETE | `/tasklists/:list_id/sections/:section_id` | 删除分组 |
| GET | `/tasklists/:list_id/tasks` | 清单里的全部任务（前端不传 `section_id`，自己按 `tasklists[].section_id` 分组） |
| POST | `/tasks/:task_id/tasklists` | `{list_id, section_id}`：加入清单或在分组间移动；**`section_id: null` 表示放到「未分组」** |
| DELETE | `/tasks/:task_id/tasklists/:list_id` | **新增**：把任务移出清单 |

清单对象：

```json
{ "list_id": "tl_1", "name": "机械臂抓取项目", "description": "", "project_record_id": null,
  "created_by": "ou_admin", "created_at": "...", "updated_at": "...",
  "permissions": {"can_view": true, "can_edit": true, "can_manage": true, "can_delete": true} }
```

前端按下面的规则实现，请后端照此处理：
1. **新建清单时后端自动建 3 个默认分组**「待开始 / 进行中 / 已完成」（模拟后端就是这样）。不建也行，前端会显示空状态，引导用户「新建分组」。
2. **删除清单只移除关联，不删任务**（前端确认框就是这样写的）。
3. **删除分组时，里面的任务移到「未分组」**（`section_id` 变成 null），不删任务。前端把 `section_id` 为空或指向不存在分组的任务都显示在「未分组」。
4. 一个任务可以在多个清单里，每个清单的分组互相独立；在清单里拖动只改这个清单的 `section_id`，**不改任务状态**。
5. 分组重名请返回 409 `SECTION_NAME_EXISTS`。
6. 权限：`can_edit` 可以新建分组、添加 / 移动 / 移出任务；`can_manage` 可以改名、管成员、删除清单。清单编辑者也能改清单里的任务（`task.permissions.can_edit` 请据此计算）。
7. 在清单的某个分组里快速添加任务，前端是两步：`POST /tasks` → `POST /tasks/:id/tasklists`。如果第二步失败，任务会留在「我负责的」里，前端会提示错误。后端如愿意，可以让 `POST /tasks` 直接接受 `{list_id, section_id}`，前端再改成一步。

**暂未实现**：分组拖动排序（原文没定义接口）、清单关联 `Projects` 记录的界面（字段 `project_record_id` 已预留，接口 `GET /tasklists?project_record_id=` 已封装）。

## 5. 实时事件

前端已处理（收到后刷新任务列表、清单视图）：

| 事件 | 载荷 | 前端动作 |
|---|---|---|
| `task.created` / `task.updated` / `task.deleted` | `{task_id}`（子任务变化时也请对父任务发一次 `task.updated`） | 重新拉列表和当前清单 |
