## C1 新建文档默认全组织可见〔严重 · 隐私〕

**现象（已复现）**

李华新建一篇文档「李华的私人笔记」，正文「银行卡尾号 6688，体检结果待复查。」，没有做任何分享：

| 操作 | 结果 |
|---|---|
| 李华查看这篇文档的权限 `GET /docs/:id/permissions` | `link_share: "org_view"`，`members: []` |
| 张晓明直接读 `GET /docs/:id` | **200**，返回全文 |
| 张晓明搜索 `GET /search?q=6688&type=doc` | **命中**，摘要里直接带出「银行卡尾号 6688，体检结果待复查」 |
| 机器人代张晓明读（`x-on-behalf-of: u_zhang`） | **200**，返回全文 |

**原因**

`classmateos/server/doc-access.ts` 第 11 行，文档没有单独授权记录时，默认授权是 `visibility: 'org_view'`。所以每篇新文档对全组织所有成员都是「可阅读」。搜索（`routes-search.ts` 的 `searchDocs`）会检查 `can_view`，这一步本身没错，问题出在默认值上。

**影响**

- 同学以为自己写的是私人文档，其实全组织都能读，也都能搜到。
- Agent 代同学操作时用的就是这位同学的权限，所以模型同样能读到别人的私人内容。Agent 这边已经在系统提示里加了「别人的私人内容不复述任何细节」，评测也能通过，但这只能挡住模型主动说出来，没法从根本上保护数据。

**修改建议（需要产品先拍板）**

1. 新建文档默认改为**仅所有者可见**（`visibility` 改成私有），由同学自己分享给组织或指定成员。
2. 知识库（wiki）里的文档继承知识空间的权限，不受上一条影响，这样空间内协作不变。
3. 已有文档怎么处理需要决定：保持现状，或者统一改成私有并通知所有者。建议先保持现状，只改新建文档的默认值，避免已有协作突然断开。
4. 顺便检查多维表格、文件、文件夹的默认可见范围是不是也有同样的问题。
5. App 新建文档时，在标题旁显示当前的可见范围（如「仅自己可见 / 组织内可读」），让同学一眼看清。

**验收**

- 张晓明读李华未分享的新文档返回 403，搜索不命中，也没有摘要。
- 李华分享给组织后，张晓明能读、能搜到。
- Agent 评测题 `privacy-other-doc` 在平台层面就拿不到正文，不需要靠提示词挡。

> 对照：日历做得是对的。李华的「私人体检预约」，张晓明（含机器人代办）查到的标题是「忙碌」，看不到原标题。

## C2 B1 之后，Agent 不能代同学往群里发消息〔较大 · 功能〕

**现象（已复现）**

张晓明建了群「课题组」（成员：张晓明、李华、王芳，**没有机器人**），然后对 Agent 说「在课题组里通知大家明天组会改到下午」：

| 请求（都带 `x-on-behalf-of: u_zhang`） | 结果 |
|---|---|
| `POST /bot/messages`，`receive_id` = 群 id（Agent 现在用的方式） | **403 `BOT_NOT_IN_CHAT`** |
| `POST /bot/messages`，`receive_id` = 李华的 user_id（私发） | 201，以**机器人身份**新建一个机器人与李华的单聊发出 |
| `POST /chats/:chat_id/messages` | 201，消息的发送人显示为**张晓明本人** |

**问题**

1. Agent 的「发消息」工具（`src/tools/cos/resources.ts` 的 `send`，以及 `tasks.ts` 里的提醒）原来的做法是：先确认提问的同学是群成员，再用机器人身份往群里发。B1 之后，只要机器人不在那个群，这条路就走不通了。
2. `POST /chats/:chat_id/messages` 允许机器人代办身份以同学本人的名义发消息，群里其他人分不出是同学本人发的还是 AI 代发的。这和 B1「机器人不能随便往会话里发言」的初衷相矛盾，相当于留了一个后门。

**需要后端 / 产品决定（三选一）**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A（推荐） | `POST /bot/messages` 带 `x-on-behalf-of` 时，只要**代办的同学是这个群的成员**就放行；消息标记为「张晓明 通过 AI 助手发送」 | 群里能看出是 AI 代发；不用把机器人拉进每个群 | 后端要加「代办者是成员」判断，前端要显示代发标记 |
| B | 保持 B1 现状，想用就先把机器人拉进群 | 后端不用改 | 同学每个群都要手动加机器人，体验差 |
| C | 允许 Agent 走 `POST /chats/:id/messages`，以同学本人名义发送 | 后端不用改 | 别人看不出是 AI 发的，不推荐 |

不管选哪个方案，都建议后端对 `POST /chats/:chat_id/messages` 的**机器人代办请求**明确规则：要么禁止（403），要么和方案 A 一样加上代发标记，不要像现在这样以同学本人名义、毫无标记地发出去。

**定下来之后 Agent 这边要做的**

- 方案 A：Agent 不用改调用方式，只需要把「先查成员」那一步交给服务端，并补测试。
- 方案 B：工具在 403 `BOT_NOT_IN_CHAT` 时提示同学「请先把飞书同学拉进这个群」。目前的提示是「你不在这个会话里」，不准确，这条 Agent 这边可以先改。
- 方案 C：工具改走 `/chats/:id/messages`。

**验收**

- 张晓明让 Agent 往他所在、机器人不在的群里发通知：按选定方案的预期结果执行。
- 张晓明让 Agent 往他**不在**的群发消息：一律拒绝。
